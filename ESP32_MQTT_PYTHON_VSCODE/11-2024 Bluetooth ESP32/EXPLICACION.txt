1. GENERACIÓN Y MANEJO DEL ESP32_ID (esp32_id_manager.py)
```python
Flujo detallado:
- Durante el primer arranque del ESP32, ESP32IdManager verifica si existe 'esp32_id.json'
- Si no existe, genera un ID único combinando:
  * MAC address del ESP32 (usando machine.unique_id())
  * Timestamp del RTC
  * Formato: ESP32_{mac}_{timestamp}
- Guarda el ID en 'esp32_id.json'
- En arranques posteriores, siempre lee el ID del archivo
- Este ID NUNCA cambia durante toda la vida del dispositivo
```

2. SISTEMA DE REINTENTOS (wifi_manager.py)
```python
Parámetros de control:
- CONNECTION_TIMEOUT = 20000 (20 segundos por intento)
- RETRY_INTERVAL = 5000 (5 segundos entre reintentos)
- MAX_RETRIES = 3 (intentos máximos)

Proceso detallado:
a) Primer nivel de reintentos (connect_wifi):
   - Intenta conectar
   - Espera 20 segundos máximo
   - Si falla, retorna False

b) Segundo nivel (ensure_wifi_connected):
   - Hace 3 intentos máximo
   - Entre cada intento espera 5 segundos
   - Incrementa reconnection_attempts
   - Registra last_disconnect_reason

c) Tercer nivel (main.py - try_wifi_connection):
   - 5 intentos máximos
   - Tiempo de espera progresivo: 5s, 10s, 15s, 20s, 25s
   - Si falla todos los intentos, vuelve a modo configuración
```

3. PROCESO DE ARRANQUE DETALLADO:
```python
a) Inicialización (Orden exacto):
   1. ESP32 bootea -> boot.py (si existe) -> main.py
   2. Inicialización de managers en orden:
      - ESP32IdManager (primero para tener ID disponible)
      - WiFiManager
      - WatchdogManager (timeout 120 segundos)
      - SystemManager
      - RelayManager
      - PerformanceMonitor
      - ConnectionMonitor
      - MQTTManager

b) Verificación de Configuración:
   1. Busca wifi_config.json
   2. Busca panel_config.json
   3. Si falta alguno, entra a modo configuración

c) Modo Configuración Bluetooth:
   1. Activa BLE con nombre "ESP32-HDD"
   2. Configura servicio UART BLE
   3. Buffer de recepción: 4096 bytes
   4. Espera datos JSON con formato:
      {START}{"ssid":"xxx","password":"xxx"}{END}
   5. Timeout de espera: 300 segundos
```

4. MANEJO DE ESTADOS Y ERRORES:
```python
Estados del Sistema:
- INITIAL: Arrancando
- WIFI_CONFIG: Configurando WiFi vía BLE
- MQTT_CONFIG: Configurando panel vía MQTT
- RUNNING: Operación normal
- ERROR: Estado de error
- UPDATING: Actualizando firmware

Manejo de Errores:
a) WiFi:
   - Desconexiones
   - Credenciales inválidas
   - Timeout de conexión
   - Red no encontrada

b) MQTT:
   - Cola de mensajes pendientes
   - Reintentos de conexión
   - LWT (Last Will and Testament)

c) Sistema:
   - Watchdog cada 5 segundos
   - GC (Garbage Collection) cada 5 minutos
   - Monitoreo de memoria libre
```

5. MONITOREO Y MÉTRICAS:
```python
a) Métricas de Sistema:
   - Memoria libre/usada
   - Tiempo de ejecución
   - Conteo de reinicios
   - Causa del último reinicio

b) Métricas de Conexión:
   - Estado WiFi
   - Fuerza de señal (RSSI)
   - Intentos de reconexión
   - Última razón de desconexión

c) Métricas de Relés:
   - Estado actual
   - Último cambio
   - Historial de cambios (últimos 50)
   - Eventos pendientes
```

6. SINCRONIZACIÓN DE TIEMPO:
```python
Proceso:
1. Intenta obtener hora de worldtimeapi.org
2. Si falla, intenta con timeapi.io
3. Si ambos fallan, usa RTC interno
4. Actualiza cada 5 minutos (TIME_SYNC_INTERVAL = 300000)
```

7. PERSISTENCIA DE DATOS:
```python
Archivos críticos:
- esp32_id.json: ID único del dispositivo
- wifi_config.json: Configuración WiFi
- panel_config.json: Configuración del panel
- boot_count.txt: Contador de reinicios
- update_status.json: Estado de actualizaciones
```

   ::::::::::::::::::::::::::::::::::::::::::::::::::::::::::::::: CAPAS DE FUNCIONAMIENTO Y CARACTERISTICAS DE SEGURIDAD :::::::::::::::::::::::::::::::::::::::::::::::::::::::::::

   El ESP32 en este sistema tiene varias capas de funcionamiento y características de seguridad. Te explicaré en detalle:

Modo Seguro (Safe Mode):

Se activa cuando detecta patrones anormales de funcionamiento (ej: múltiples resets en poco tiempo)
Reduce la funcionalidad a lo mínimo necesario
Aumenta la frecuencia del watchdog
Libera memoria
Notifica al servidor del problema
Es una "última línea de defensa" antes de un fallo total


Sistema de Watchdog:

Monitorea que el sistema esté respondiendo
Si no recibe "alimentación" en el tiempo establecido, fuerza un reset
Ayuda a recuperar el sistema de bloqueos
Tiene conteo de resets para detectar problemas recurrentes


Gestión de Memoria:

Monitoreo constante del uso de memoria
Garbage collection proactivo
Umbrales de memoria libre/usada
Prevención de fragmentación


Sistema de Respaldo:

Archivos de configuración duplicados (.json y .bak)
Validación de datos antes de guardar
Archivos temporales para escritura segura
Recuperación automática si hay corrupción


Estados de Operación:

Normal: Funcionamiento completo
Configuración: Solo BLE activo para setup
Seguro: Funcionalidad reducida
Error: Intento de recuperación antes de reset


Características Ocultas:

Detección de interferencia en señales
Conteo de errores de comunicación
Auto-diagnóstico de hardware
Sistema de logs en memoria
Recuperación automática de conexiones


Protecciones de Hardware:

Debouncing en señales de entrada
Filtrado de ruido eléctrico
Protección contra picos de voltaje
Monitoreo de temperatura


Sistema de Alertas:

Niveles de criticidad
Alertas inmediatas para problemas graves
Buffer de eventos para envío posterior
Registro de incidentes históricos


Optimizaciones:

Sleep modes para ahorro de energía
Priorización de tareas críticas
Caché de datos frecuentes
Buffers optimizados


Recuperación de Fallos:

Sistema de fallback para conexiones
Reintentos inteligentes
Restauración de estado anterior
Aislamiento de componentes fallidos


Diagnóstico Remoto:

Envío de métricas detalladas
Estado de componentes
Historial de errores
Capacidad de debug remoto


Mantenimiento Preventivo:

Detección temprana de problemas
Limpieza periódica de memoria

Todo esto funciona en conjunto para garantizar que el sistema:

Preserve la integridad de los datos
Notifique problemas oportunamente























"esp32/available": El ESP32 publica en este tópico su estado de disponibilidad durante la configuración. No se suscribe a él.
"esp32/config/{esp32_id}": Tópico específico para cada ESP32, basado en su ID único. El ESP32 se suscribe a este tópico durante la configuración para recibir su configuración específica de panel.
"clients/{client_id}/panels/{panel_id}": Este es el tópico de operación. Es específico para cada panel según su clientId y panelId, que se reciben en la configuración a través de "esp32/config/{esp32_id}". El ESP32 se suscribe a este tópico después de recibir su configuración y lo utiliza para publicar sus mensajes de estado y recibir comandos.
"system/stats/{esp32_id}": El ESP32 publica periódicamente estadísticas del sistema en este tópico, que también es específico para cada dispositivo según su ID.
"system/alerts/{esp32_id}": El ESP32 publica alertas del sistema en este tópico, de nuevo específico para cada dispositivo.
